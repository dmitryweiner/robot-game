# CLAUDE.md — карта проекта для агента

«Помоги роботу» — браузерная игра по мотивам книги
[robot-talks](../robot-talks) (`Д. Обский, claude-opus-4-7, GPT-5.5
Thinking`): мальчик помогает роботу чинить вещи и по пути осваивает Linux,
программирование и разные концепции CS. Игра — набор текстовых/минимально-
графических мини-игр, **одна глава книги = одна мини-игра**, кроме первой
(00, вступление) и последней (09, эпилог) глав.

Исходное ТЗ пользователя — в `INITIAL.md` в корне репозитория, перечитай его
первым делом, там есть требования, которые легко упустить (стиль, TDD,
структура `documentation/`). Дизайн — 8-битные консоли/старые терминалы:
ярко-зелёным по чёрному фону, спрайтовая 2D-графика (когда нужна), 1-битный
звук как из PC speaker (звук пока нигде не реализован — до него не дошли).

Полезные соседние репозитории (весь путь эволюции решений в них):
- `../robot-talks/0N. *.md` — тексты глав (источник сюжета и материала для
  каждой мини-игры). `../robot-talks/source-chats/` — более развёрнутые
  QA-обсуждения тех же тем (там больше технических деталей, если в главе
  что-то сжато). **Внимание: нумерация файлов в `source-chats/` смещена на
  единицу относительно глав книги** (глава 00 не имеет своего файла в
  source-chats, поэтому `source-chats/01. *.md` соответствует главе `02.
  *.md`, `source-chats/02. *.md` — главе `03.md`, и так далее) — сверяйся по
  содержанию, а не по номеру в имени файла.
- `../formula-synth` — образец инфраструктуры (Vite/TS/Vitest/ESLint/
  Playwright-скрипты, сборка в `./docs` для GitHub Pages), с которого списана
  конфигурация этого проекта. Он на vanilla TS, не React — при заимствовании
  паттернов адаптируй под React, не копируй бездумно.

## Ключевые решения, принятые пользователем (не переспрашивать)

- Язык интерфейса и всех игровых текстов — **русский**.
- Структура — **один React SPA-хаб**, роутинг между главами внутри одного
  приложения (не отдельные сборки на игру). Прогресс — `localStorage`,
  бэкенда нет.
- Разработка — **TDD**: сначала тест, потом код. Визуальные/e2e-тесты —
  Playwright (`tests-e2e/`), юнит/компонентные — Vitest + Testing Library
  (`tests/`).
- Инфраструктура — по образцу `../formula-synth`, но версии пакетов взяты
  актуальные на момент установки (см. `package.json`; экосистема ушла
  вперёд — например, TypeScript оставлен на `^5.9.3`, а не на мажорной `7.x`,
  которая уже есть в npm, но пока сыровата в связке с остальным тулингом;
  Node — `v20.20.2`, поэтому `jsdom`/`@testing-library/jest-dom` пришлось
  прижать к версиям, которые ещё не требуют Node 22+).
- ESLint: `@typescript-eslint/consistent-type-assertions` с
  `assertionStyle: 'never'` — **`as`-касты и угловые скобки запрещены**
  везде, включая тесты. Используй сужение типов (`instanceof`, `typeof`,
  `in`-narrowing) — примеры есть в `src/progress/progress.ts` и
  `tests/components/Terminal.test.tsx` (`getInput()`).
- react-hooks/eslint строго следит за `setState` внутри `useEffect` для
  сброса состояния по смене пропа — правильный паттерн здесь **не** эффект,
  а `key={...}` на дочернем компоненте, чтобы React сам его пересоздал (см.
  `HintButton` + его использование в `RepairConsoleGame.tsx`).
- Коммитить только по явной просьбе пользователя. Инфраструктура + игра 1
  (со всеми описанными здесь доработками) уже закоммичены одним коммитом
  29.07.2026 — дальше по умолчанию снова ничего не коммить без спроса. Игра 2
  (глава 02) реализована в сессии от 29.07.2026, но **не закоммичена** —
  дождись явной просьбы.
- После значимых UI-изменений — открывать приложение в браузере
  (`npm run dev`) и вручную проходить сценарий через `mcp__claude-in-chrome__*`
  инструменты, не полагаться только на автотесты. Так в игре 2 обнаружился
  реальный визуальный баг с SVG-иллюстрацией (см. запись про
  `transform`-ловушку выше) — юнит- и e2e-тесты его не ловили, потому что не
  проверяют фактический рендеринг CSS-анимаций.
- Визуальный мотив иллюстрации главы — решение пользователя, а не агента:
  для игры 1 это был робот (по умолчанию, тема не уточнялась), для игры 2
  пользователь сам явно указал «схематичный контроллер и мотор насоса» в
  постановке задачи. Если для новой главы мотив не очевиден из текста
  главы и не задан пользователем прямо — спроси, не выбирай сам.

## Обратная связь пользователя из этой сессии (важно на будущее)

- Интро — **два уровня, не один**. Сначала было "по попапу на каждую главу
  с полным сюжетом" — пользователь после ревью явно попросил разделить:
  (1) **глобальный** попап (`components/GlobalIntro.tsx`) — кто мальчик и
  робот, за кого играет пользователь (за мальчика, как в книге — это прямо
  уточнялось отдельным вопросом, не додумывай иначе), общая завязка, ссылка
  на книгу (`https://dmitryweiner.github.io/robot-talks/`); показывается
  **автоматически один раз** при первом визите на сайт (`Progress.introSeen`
  в `localStorage`) и по кнопке «Введение» в хабе — дальше; (2) попап
  **каждой главы** (`StoryIntro.tsx` внутри папки игры) — без общих слов,
  только специфика этой главы: что случилось и что делать, какие средства
  доступны игроку; показывается при каждом входе в игру. Общий
  `components/Modal.tsx` — переиспользуй для обоих уровней. Подробности —
  `documentation/ARCHITECTURE.md` → «Интро: два уровня».
- В каждой мини-игре должна быть **небольшая анимированная иллюстрация**,
  которая меняется по мере прогресса игрока (не статичная картинка). В игре
  1 это лежащий/поднимающийся робот. Механизм: чистая функция
  прогресс → «поза» (`pose.ts`) + компонент, рендерящий её. Сейчас
  реализовано инлайн-SVG-примитивами — это **осознанный плейсхолдер**, не
  «правильный» спрайтовый арт (в этой сессии не было инструментов для
  генерации пиксель-арта); если появится способ сделать/сгенерировать
  настоящие PNG-спрайты — заменить компонент рендеринга, не логику позы.
- Нужна **кнопка `(?)`**, которая по клику показывает точный ответ (что
  именно набрать в консоли), но без возможности скопировать текст — паттерн
  `HintButton.tsx` (стиль `userSelect: 'none'` + блокировка `onCopy`/
  `onContextMenu`; это защита от случайного Ctrl+C, не DRM).
- Пользователь ожидает **полного погружения** в терминал: например, `Tab` в
  игровой консоли не должен уводить фокус браузера на другой элемент
  страницы — должен работать как в настоящем шелле (у нас — автодополнение
  команд/путей, `shell/complete.ts`). Держи в уме этот дух при добавлении
  новых мини-игр с похожим вводом: клавиши, которые в браузере что-то
  «перехватывают» по умолчанию (Tab, возможно Ctrl+L/Ctrl+C в будущем), стоит
  явно обрабатывать самим, если это уместно для жанра игры.
- В сайдбаре игры должна быть **справка по командам** — ссылка(-и) на
  «man page» команд, доступных в этой главе. Пользователь сначала предложил
  «ссылку» (в единственном числе), но тут же уточнил: **ссылок должно быть
  несколько** — по одной на команду/оператор, каждая открывает свой попап
  (`components/CommandReference.tsx` + `components/ManLinks.tsx`, данные —
  `game-NN-*/manPages.ts`). Не делай один общий попап со списком всех команд
  сразу — уже пробовали, попросили переделать. Держи `manPages.ts` в
  соответствии с `COMMAND_NAMES` через тест-инвариант (см. `tests/shell/
  manPages.test.ts` как образец).
- Пользователь пишет короткими репликами по-русски, ожидает, что агент сам
  восстановит контекст, задаёт уточняющие вопросы только когда решение
  реально неоднозначно (см. `AskUserQuestion` в начале этой сессии — три
  вопроса: язык UI, структура приложения, с чего начать; и позже — вопрос
  «за кого играем», когда формулировка пользователя противоречила уже
  реализованному) — не нужно спрашивать повторно то, что уже решено выше.
  При этом мелкие уточнения формулировок («ссылки», не «ссылку») пользователь
  присылает следом, почти сразу после основного сообщения — читай такие
  добавления как часть того же запроса, а не как новую задачу.

## Команды

```bash
npm run dev             # Vite dev-сервер
npm run build            # tsc --noEmit && vite build → ./docs (для GitHub Pages)
npm test                 # vitest run (юнит/компонентные)
npm run test:watch       # vitest в watch-режиме
npm run lint              # eslint .
npm run check             # tsc --noEmit && eslint . && vitest run — гонять после каждой правки
npm run e2e                # playwright test (нужен `npx playwright install chromium` один раз)
npx playwright test --update-snapshots   # перегенерировать визуальные baseline-скриншоты
```

## Карта каталогов

```
INITIAL.md                     Исходное ТЗ пользователя — начни с него
documentation/
  ARCHITECTURE.md               Текущая архитектура — держать в актуальном состоянии
  plans/game-NN-*.md             План на каждую фичу/главу (перед реализацией)
  features/game-NN-*.md          Как фича устроена по факту (после реализации)
src/
  App.tsx, main.tsx               Точка входа, хеш-роутинг хаб/игра
  styles/terminal.css              Глобальная тема (зелёный на чёрном, CRT)
  routing/useHashRoute.ts          Самодельный хеш-роутер (#/, #/game/<id>)
  progress/progress.ts             localStorage-прогресс (completedGameIds, introSeen)
  components/Hub.tsx, Modal.tsx,    Хаб-меню; переиспользуемый диалог;
    GlobalIntro.tsx,                 общий попап о мире (см. «Интро: два уровня»);
    CommandReference.tsx,            попап man-страницы одной команды;
    ManLinks.tsx                     строка man-ссылок для сайдбара игры
  games/
    types.ts, registry.ts           Контракт мини-игры + список игр по порядку
    game-01-repair-console/          Первая мини-игра — образец структуры для новых
tests/                            Vitest + Testing Library, зеркалит src/
tests-e2e/                        Playwright (визуальные/e2e)
```

Чтобы добавить новую мини-игру: создать `src/games/game-NN-<slug>/` с
компонентом вида `GameProps -> { onComplete: () => void }`, добавить запись в
`GAMES` в `src/games/registry.ts` (порядок в массиве = порядок разблокировки
через `isGameUnlocked`). Подробнее — `documentation/ARCHITECTURE.md`.
